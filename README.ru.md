# ZigbeeMQTTlink

[English](README.md) · **Русский**

Сервис для связи действующей Zigbee-сети с MQTT. Включает веб-панель, отдельную JSON-базу устройств и описания моделей, которые можно обновлять без пересборки.

ZigbeeMQTTlink напрямую взаимодействует с координатором **TI Z-Stack** через UART или TCP. Для запуска не нужны Node.js и Zigbee2MQTT. Внешние скрипты получают сообщения устройств и отправляют команды по MQTT; правила автоматизации остаются в этих скриптах.

## Возможности и границы поддержки

- Прямой обмен по Zigbee ZNP/ZCL и подключение к MQTT 3.1.1.
- Приём отчётов, отправка команд, определение модели/производителя и опрос endpoints.
- Веб-список устройств, просмотр состояний, команды, переименование, калибровки, удаление и замена.
- Временное открытие сопряжения; при запуске подключение новых устройств закрыто.
- Отдельные JSON-файлы для основного конфига, базы и описаний моделей.
- Описания ZCL/Tuya: атрибуты, скалярные команды, события, datapoints, коэффициенты, ограничения и действия настройки.
- Сохранение и перечитывание описаний через веб/MQTT без перезапуска и с предварительной проверкой.
- Построчные JSON-логи: уровень детализации, файл, ротация и вывод в консоль.
- Сохранение MQTT-имени при замене устройства совместимым.
- Игнорирование retained-команд; принятие команды транспортом не выдаётся за подтверждённое физическое состояние.

Версия использует **уже созданную действующую сеть**. Создание/восстановление сети, другие протоколы координаторов, OTA, группы/сцены и полный процесс binding/IAS enrollment не реализованы. Home Assistant discovery отсутствует. В проекте нет YAML-конфига, импортёра database.db, симулятора и набора тестов.

JSON расширяет поддержанные форматы ZCL и Tuya DP. Новые закрытые handshake, шифрование, вложенные vendor-данные и другие адаптеры могут потребовать изменений Go. Одинаковый model_id не гарантирует одинаковое поведение разных производителей и прошивок.

## Требования

Для готового бинарника:

- Linux AMD64 или ARM64.
- Координатор TI Z-Stack с действующей Zigbee-сетью.
- Доступ к UART, например `/dev/ttyUSB0`, или TCP-подключению последовательного порта.
- Доступный MQTT-брокер.
- Права записи в каталоги базы, описаний и логов.

Для сборки: **Go 1.25.1 или новее**. Зависимости подключаются через Go modules; каталога `vendor` нет. При первой сборке нужен доступ к загрузке модулей, если их ещё нет в локальном кэше. Готовые бинарники не загружают зависимости при запуске.

## Быстрый запуск

1. Распакуйте архив или получите исходники и соберите проект.
2. Настройте `config.json`: MQTT, учётные данные, координатор и пути. Замените `CHANGE_ME`, если используете параметры подключения из поставляемого примера.
3. При переносе остановите прежний сервис и сохраните его рабочую базу, как описано ниже. Поставляемый `devices.json` — **пустой пример**.
4. Проверьте файлы и запустите:

```bash
cd ZigbeeMQTTlink
chmod +x ./dist/zigbeemqttlink-linux-amd64
./dist/zigbeemqttlink-linux-amd64 -check-config -config ./config.json
./dist/zigbeemqttlink-linux-amd64 -config ./config.json
```

На ARM64 используйте `zigbeemqttlink-linux-arm64`. При настройках веба из примера: `http://АДРЕС_СЕРВЕРА:8080`.

`-check-config` не открывает радио и не подключается к MQTT. Команда выводит число описаний моделей и устройств в базе. При переносе количество устройств должно совпасть с рабочей базой. `devices=0` допустимо для новой пустой базы; такой файл не должен заменять записи действующей установки.

### Перенос действующей Go-версии

JSON-формат version=1 прежнего файла `native-state.json` принимается напрямую. Остановите прежний сервис, сделайте резервную копию и скопируйте файл в `devices.json` либо задайте его полный путь в `database`. При том же координаторе и действующей сети конвертация и повторное сопряжение не требуются.

Это совместимость с JSON-базой **Go-версии**, а не с `database.db` оригинального Zigbee2MQTT. Импортёр удалён. Нельзя одновременно запускать два процесса на одном координаторе, даже с разными файлами базы.

В поставляемом конфиге `mqtt.base_topic: "zigbee2mqtt"` сохранён для существующих скриптов. Это MQTT-пространство, а не зависимость от другого проекта. Чтобы использовать `zigbeemqttlink`, одновременно измените конфиг и подписки/публикации скриптов. MQTT client ID и стандартное имя лога уже используют новое имя проекта.

## Сборка из исходников

Выполняйте команды из корня, где находятся `main.go` и `go.mod`:

```bash
go mod download
go build -buildvcs=false -trimpath -o dist/zigbeemqttlink .
./dist/zigbeemqttlink -check-config -config ./config.json
./dist/zigbeemqttlink -config ./config.json
```

Для разработки: `go run -buildvcs=false . -config ./config.json`. Опция сборки `-buildvcs=false` позволяет собирать распакованные исходники без Git-метаданных.

| Команда | Результат |
|---|---|
| `make build` | Локальный статический бинарник `dist/zigbeemqttlink` |
| `make release` | Статические сборки Linux AMD64/ARM64 и `dist/SHA256SUMS` |
| `make vet` | Статический анализ Go |

Сборка под другие архитектуры без Make:

```bash
CGO_ENABLED=0 GOOS=linux GOARCH=amd64 go build -buildvcs=false -trimpath -ldflags='-s -w' -o dist/zigbeemqttlink-linux-amd64 .
CGO_ENABLED=0 GOOS=linux GOARCH=arm64 go build -buildvcs=false -trimpath -ldflags='-s -w' -o dist/zigbeemqttlink-linux-arm64 .
```

`go build` создаёт каталог результата. Доступны флаги `-config`, `-check-config`, `-version`. Детализация логов задаётся в JSON; флагов `-debug` и `-import-db` нет.

## Конфигурация

Пример основного конфига; настройте подключения и пути под свою установку:

```json
{
  "version": 1,
  "database": "devices.json",
  "device_definitions": "device-definitions.json",
  "mqtt": {
    "server": "mqtt://localhost:1883",
    "base_topic": "zigbee2mqtt",
    "client_id": "zigbeemqttlink"
  },
  "serial": {"port": "/dev/ttyUSB0", "baudrate": 115200},
  "web": {"enabled": true, "listen": "0.0.0.0:8080"},
  "logging": {
    "level": "info",
    "file": "logs/zigbeemqttlink.log",
    "console": true,
    "max_size_mb": 10,
    "backups": 3
  }
}
```

| Параметр | Назначение |
|---|---|
| `version` | Версия схемы: `1` |
| `database` | Точный путь к отдельному JSON-файлу базы |
| `device_definitions` | Путь к загружаемым описаниям моделей |
| `mqtt.server` | `mqtt://HOST[:PORT]` или `mqtts://HOST[:PORT]`; также `tcp`/`ssl` |
| `mqtt.base_topic` | Пространство топиков сервиса и скриптов |
| `mqtt.client_id` | Уникальный ID клиента |
| `mqtt.user`, `mqtt.password` | Необязательные учётные данные брокера |
| `mqtt.ca` | Необязательный файл доверенного CA |
| `mqtt.cert`, `mqtt.key` | Сертификат/ключ клиента; задаются вместе |
| `mqtt.server_name` | Необязательное переопределение имени TLS-сервера |
| `mqtt.force_disable_retain` | Отключить retain обычных публикаций и Last Will |
| `serial.port` | UART или `tcp://HOST:PORT` для последовательного интерфейса TI Z-Stack |
| `serial.baudrate` | Скорость UART, обычно `115200` |
| `web.enabled`, `web.listen` | Включение HTTP и адрес/порт прослушивания |
| `logging.level` | `debug`, `info`, `warn`, `error` |
| `logging.file`, `logging.console` | Файл и/или вывод в stderr |
| `logging.max_size_mb`, `logging.backups` | Порог ротации и число старых файлов |

Относительные файловые пути отсчитываются от каталога `config.json`, а не от рабочей директории процесса. Это относится и к относительным UART-путям; адрес `tcp://` остаётся адресом. Пути базы, описаний, лога и основного конфига должны различаться.

Стандартные MQTT-порты: `1883` без TLS, `8883` с TLS. Сертификат брокера проверяется, используется TLS 1.2 или новее. Протокол MQTT — 3.1.1. Учётные данные задаются отдельными полями, а не внутри URL брокера.

Пространство по умолчанию в коде — `zigbeemqttlink`; в поставляемом конфиге явно выбрано `zigbee2mqtt` для совместимости. Лишние поля, повторяющиеся JSON-ключи, неподдержанные версии, комментарии и дополнительные значения после объекта отклоняются. Старые YAML/Home Assistant/queue/advanced параметры не игнорируются молча.

Изменения основного конфига требуют перезапуска. Описания моделей перечитываются отдельно без него. PAN, канал и ключ сети остаются в действующем координаторе; создание новой сети по параметрам конфига не предусмотрено.

## База устройств

| Поле | Содержимое |
|---|---|
| `version` | Версия схемы базы: `1` |
| `coordinator_ieee` | IEEE координатора для проверки соответствия сети |
| `devices` | Записи по IEEE устройств |
| `states` | Последние состояния по IEEE |

Запись содержит `ieee_address`, `network_address`, `type` (`Router`/`EndDevice`), `friendly_name`, `model_id`, `manufacturer`, `endpoints`, `last_seen`, `options`. Поля endpoint: `ID`, `profileID`, `deviceID`, `inputClusters`, `outputClusters`, необязательные `measurement_scales`.

Пустая база:

```json
{"version":1,"coordinator_ieee":"","devices":{},"states":{}}
```

NWK и endpoints должны поступать из сети или действующей базы. Одного списка IEEE недостаточно; выдумывать NWK для записей нельзя.

Запись производится через временный файл с атомарной заменой. Файл блокировки — `ПУТЬ_БАЗЫ.lock`. Повреждённые/несогласованные данные отклоняются без перезаписи. Ручная правка базы допустима при остановленном сервисе; во время работы используйте веб/API.

### Калибровки и замена

Числовые ключи `options`:

- `temperature_calibration`, `device_temperature_calibration`, `humidity_calibration`, `pressure_calibration`: прибавляемая поправка в единицах значения.
- `illuminance_calibration`, `power_calibration`, `energy_calibration`, `voltage_calibration`, `current_calibration`: процентная поправка, `значение × (1 + поправка / 100)`.

Сначала сопрягите новое устройство, затем выберите его в панели старого и выполните замену. Должна совпадать известная модель; для `TS0601`/`TS011F` дополнительно требуется тот же известный производитель. Новому передаются старое MQTT-имя и калибровки; старая запись удаляется. Аппаратные настройки и старое физическое состояние не копируются: настройте и проверьте новое оборудование отдельно.

## Поддерживаемые модели

| Модель/производитель | Обработчик | Основные возможности |
|---|---|---|
| `lumi.switch.b2nc01` | `aqara_e1` | Левый/правый канал и поддержанные настройки Aqara |
| `lumi.relay.c2acn01` | `aqara_relay` | Два канала, interlock и поддержанные настройки |
| `lumi.weather` | `aqara_weather` | Температура, влажность, давление, батарея |
| `lumi.sensor_wleak.aq1` | `aqara_leak` | Протечка и батарея |
| `lumi.remote.b186acn02` | `aqara_button` | События кнопки `action` |
| `TS011F` | `tuya_plug` | Включение/выключение, поддержанные параметры старта и измерения |
| `TS0601`, перечисленные климатические производители | `tuya_climate` | Известные климатические DP по производителю |
| `TS0601` + `_TZE200_t1blo2bj`, `_TZE204_t1blo2bj`, `_TZE204_q76rtoa9` | JSON `neo_nas_ab02b2` | Сирена NEO: alarm, мелодия, громкость, длительность, заряд |

Списки производителей и ограничения находятся в `device-definitions.json`. Поддержка относится к конкретным вариантам и не гарантирует работу любой прошивки с тем же model_id. Для несовпавших моделей остаётся стандартный ZCL; неизвестным Tuya не отправляются предполагаемые DP-команды.

## MQTT

`BASE` — `mqtt.base_topic`; `DEVICE` — имя или IEEE. Команды публикуются **без retain**.

| Топик | Направление | Данные |
|---|---|---|
| `BASE/DEVICE` | Сервис → скрипты | JSON-состояние/отчёт |
| `BASE/DEVICE/set` | Скрипты → сервис | JSON-команда или поддержанные `ON`/`OFF`/`TOGGLE` |
| `BASE/DEVICE/get` | Скрипты → сервис | JSON с перечнем свойств |
| `BASE/DEVICE/set/PROPERTY` | Скрипты → сервис | Одно JSON-значение или поддержанное простое значение |
| `BASE/DEVICE/get/PROPERTY` | Скрипты → сервис | Пустое сообщение может запросить свойство |
| `BASE/DEVICE/CHANNEL/set` | Скрипты → сервис | Команда объявленного канала |
| `BASE/bridge/state` | Сервис → скрипты | Online/offline и Last Will |
| `BASE/bridge/info` | Сервис → скрипты | Версия, имя проекта, метаданные |
| `BASE/bridge/devices` | Сервис → скрипты | Список устройств |
| `BASE/bridge/request/REQUEST` | Скрипты → сервис | Данные административного запроса |
| `BASE/bridge/response/REQUEST` | Сервис → скрипты | `status`, `data`, необязательные `error`/`transaction` |

Примеры команд:

```json
{"state":"OFF"}
```

```json
{"state_left":"ON","state_right":"OFF"}
```

```json
{"state_l1":"OFF","state_l2":"ON"}
```

Составная команда TS011F:

```json
{"state":"OFF","power_outage_memory":"restore"}
```

Сирена NEO:

```json
{"melody":"7","volume":"high","duration":10,"alarm":true}
```

Остановка: `{"alarm":false}`. Описание задаёт отправку настроек до включения, выключения — первым. `/get` содержит имена свойств со значениями-заглушками: `{"state":"","power":""}`. Tuya `/get` запрашивает все DP; ответ зависит от прошивки и доступности устройства.

Пример Mosquitto CLI; при необходимости добавьте учётные данные:

```bash
mosquitto_sub -h BROKER_HOST -t 'zigbee2mqtt/#' -v
mosquitto_pub -h BROKER_HOST -t 'zigbee2mqtt/siren/set' -m '{"alarm":false}'
mosquitto_pub -h BROKER_HOST -t 'zigbee2mqtt/bridge/request/permit_join' -m '{"time":60}'
```

Ошибки команд устройств пишутся в лог. Административные запросы получают отдельный ответ. Принятие транспортом не подтверждает физическое действие; состояние меняется по отчёту устройства. События action публикуются без retain и не сохраняются как постоянное состояние. Обычные состояния/метаданные могут быть retained; `force_disable_retain` отключает это поведение. Очистка старых retained-имён продолжает использовать пустые retained-публикации.

## Веб-панель и HTTP API

Веб встроен в бинарник: отдельные файлы, Node.js и сборка фронтенда не нужны. Есть просмотр устройств/состояний, команды, калибровки, переименование/удаление/замена, настройка, временное сопряжение и JSON-редактор описаний.

Веб **без авторизации**, рассчитан на доверенный внутренний контур. Основной `config.json` редактируется на диске. Веб-редактор изменяет описания моделей, параметры устройств сохраняются в базе. Проверки JSON/Origin/Host для изменяющих HTTP-запросов сохранены.

| Endpoint | Назначение |
|---|---|
| `GET /api/health` | MQTT/радио/сопряжение и счётчики; 503 при нездоровом состоянии |
| `GET /api/devices` | Записи устройств |
| `GET /api/state?id=DEVICE` | Последнее состояние |
| `GET /api/admin` | Общие данные веб-панели |
| `GET /api/definitions` | Активные описания |
| `POST /api/request` | Команда или административная операция |

Пример HTTP:

```json
{"request":"device/set","data":{"id":"siren","payload":{"alarm":false}}}
```

```bash
curl -X POST http://SERVER_IP:8080/api/request \
  -H 'Content-Type: application/json' \
  -d '{"request":"permit_join","data":{"time":60}}'
```

| Запрос | Поля данных |
|---|---|
| `permit_join` | `time`: целые секунды `0..254`; `0` закрывает сопряжение |
| `health_check` | Пустой объект |
| `device/rename` | `id` (или `from`), `to` (или `friendly_name`) |
| `device/options` | `id`, `options`: калибровки |
| `device/replace` | `id`: старое; `to`: сопряжённая замена |
| `device/remove` | `id`, необязательный `force`; `true` только забывает локально |
| `device/configure` | `id` |
| `device/set`, `device/get` | `id`, `payload` |
| `definitions/reload` | Пустой объект |
| `definitions/save` | `definitions`: полное описание version/devices |

В MQTT данные отправляются напрямую в `BASE/bridge/request/REQUEST`. В HTTP используется оболочка `{"request":"REQUEST","data":{...}}`. Необязательный MQTT `transaction` повторяется в ответе. Тело HTTP — до 4 MiB; MQTT-команда — до 64 KiB. Описания проверяются до замены файла и реестра.

## Описания устройств

Пример файла:

```json
{
  "version": 1,
  "devices": [
    {
      "id": "example_temperature",
      "models": ["YOUR_SENSOR_MODEL"],
      "protocol": "zcl",
      "endpoint": 1,
      "properties": {
        "temperature": {
          "type": "number", "access": "r",
          "cluster": 1026, "attribute": 0,
          "wire_type": 41, "scale": 0.01
        }
      }
    }
  ]
}
```

Каждый `examples/*.definition.json` — **один элемент массива**, а не полный файл. Добавьте его в существующий `devices` и замените заглушки реальными параметрами протокола. Сохраните описания действующих устройств.

### Выбор модели

| Поле | Значение |
|---|---|
| `id`, `models` | Уникальный ID и обязательные точные model_id |
| `manufacturers` | Необязательные точные производители, особенно важны для Tuya |
| `protocol` | `builtin`, `zcl`, `tuya` |
| `builtin` | Специализированный обработчик, только для `builtin` |
| `endpoint` | `1..240`; без него — единственный HA endpoint с нужным входным cluster |
| `channels` | Имя → endpoint, например `{"left":1,"right":2}` |
| `properties` | Свойства MQTT и их преобразование в протокол |
| `events` | ZCL cluster-specific команды → состояние/события |
| `command_order` | Порядок составной команды; остальные имена сортируются |
| `stop_first` | Записываемое boolean-свойство; `false` отправляется первым |
| `inter_command_delay_ms` | Пауза между кадрами, `0..1000` |
| `configure` | Последовательность действий настройки |
| `gateway_status` | Tuya-ответ о состоянии шлюза |
| `time_epoch` | Ответ на запрос времени Tuya: `off`, `1970`, `2000` |

Описание с производителем приоритетнее описания только модели. Неоднозначные селекторы одного приоритета отклоняются. Для builtin допустимы селекторы, обработчик и пауза; протокольная логика остаётся в Go. Для декларативного описания используйте zcl/tuya.

При объявлении каналов задайте соответствующие свойства, например `state_left`/`state_right`, с нужными endpoints. Маршрутизация переводит `state`/`operation_mode` в имена с суффиксами; автоматически свойства не создаются.

### Свойства и типы протокола

| Поле | Значение |
|---|---|
| `type` | `boolean`, `number`, `integer`, `enum`, `string` |
| `access` | `r`: отчёт/чтение; `w`: запись; `rw`: оба направления |
| `endpoint` | Переопределение endpoint свойства |
| `cluster`, `attribute` | ZCL ID; attribute обязателен для чтения |
| `datapoint` | Уникальный Tuya DP внутри модели |
| `wire_type` | Тип скаляра ZCL / DP Tuya |
| `scale`, `offset` | Чтение: `raw × scale + offset`; scale по умолчанию `1` |
| `min`, `max` | Диапазон в единицах MQTT |
| `signed` | Tuya VALUE интерпретируется как int32 |
| `numeric_string` | Допустимы числовые строки, например `"7"` |
| `values` | Строковое enum-значение → число протокола |
| `command_ids` | ZCL enum/boolean → команда без payload |
| `write_command` | ZCL-команда с закодированным скаляром |
| `payload_prefix_hex`, `payload_suffix_hex` | Фиксированные байты вокруг скаляра |
| `manufacturer_code` | Числовой manufacturer code ZCL |

ID и типы — **десятичные JSON-числа**. Hex — строка без `0x` и пробелов. Запись: `(MQTT − offset) / scale`. Целочисленный тип требует целого результата в пределах своего размера; округления нет. Весь запрос проверяется до отправки. Ошибка транспорта после начала отправки может оставить первые кадры доставленными: аппаратной транзакцией составная команда не является.

| Протокол | Десятичный тип | Значение |
|---|---:|---|
| ZCL | `16` | Boolean (`0x10`) |
| ZCL | `32`, `33`, `35` | uint8, uint16, uint32 |
| ZCL | `40`, `41`, `43` | int8, int16, int32 |
| ZCL | `48` | enum8 |
| ZCL | `66` | UTF-8 CHAR STRING |
| Tuya | `1` | BOOL: 1 байт |
| Tuya | `2` | VALUE: 4 байта big-endian |
| Tuya | `3` | UTF-8 STRING |
| Tuya | `4` | ENUM: 1 байт |
| Tuya | `5` | BITMAP: 4 байта big-endian |

ZCL OCTET имеет hex-представление. Коллекции/структуры не являются скалярными свойствами описания. DP и единицы Tuya необходимо определить для конкретного производителя; примеры не являются универсальной схемой.

### Примеры, события и настройка

| Пример | Поведение |
|---|---|
| [zcl-light.definition.json](examples/zcl-light.definition.json) | Включение/выключение/переключение и яркость без перехода |
| [zcl-climate.definition.json](examples/zcl-climate.definition.json) | Стандартные температура/влажность, scale `0.01` |
| [zcl-button.definition.json](examples/zcl-button.definition.json) | Команды cluster 6 → `action` |
| [tuya-sensor.definition.json](examples/tuya-sensor.definition.json) | Условные DP1/DP2, отрицательная температура и ответ времени |

Пример события:

```json
{"endpoint":1,"cluster":6,"command":2,"payload_hex":"","state":{"action":"toggle"}}
```

Без `payload_hex` подходит любой payload; `""` — только пустой. События сопоставляются с cluster-specific командами, а не отчётами атрибутов. Manufacturer code по умолчанию `0`; без endpoint подходит любой endpoint. Совпавшие события применяются по порядку, последнее повторённое поле побеждает. Значения состояния — плоские скаляры.

Пример массива `configure`; это иллюстрация формата, а не универсальная настройка:

```json
[
  {"kind":"read","endpoint":1,"cluster":0,"attributes":[4,5]},
  {"kind":"write","endpoint":1,"cluster":6,"attribute":32768,"wire_type":48,"value":1},
  {"kind":"command","endpoint":1,"cluster":6,"command":1,"payload_hex":""},
  {"kind":"tuya_query","endpoint":1}
]
```

read запрашивает атрибуты, write записывает скаляр, command отправляет статическую cluster-specific команду, tuya_query запрашивает все DP. Для ZCL доступен manufacturer_code; без endpoint используется endpoint модели. Чтение атрибутов само не настраивает binding и периодические отчёты.

NEO: DP13 → alarm, DP21 → melody, DP5 → volume, DP7 → duration, DP15 → battpercentage. Ограничения и порядок записи меняются в JSON.

### Добавление модели без пересборки

1. Определите model/manufacturer/endpoints и документированные атрибуты/DP. При необходимости посмотрите debug-логи.
2. Добавьте описание и перечитайте через веб либо `BASE/bridge/request/definitions/reload` с `{}`.
3. Для нового оборудования временно откройте сопряжение и активируйте pairing устройства. Описание не создаёт физический узел и не назначает NWK.
4. Дождитесь определения модели, при необходимости разбудите батарейное устройство и выполните настройку.
5. Проверьте реальные сообщения/команды и закройте сопряжение.

Веб сохраняет файл атомарно после проверки и затем активирует его. Ошибочное сохранение/перечитывание оставляет прежний реестр. Исправьте неверную ручную правку перед перезапуском: старт также проверяет описания. Перечитывание не перенастраивает автоматически все существующие устройства.

## Логирование

Каждая строка — JSON со временем, уровнем, сообщением и параметрами операции.

| Уровень | Детализация |
|---|---|
| `debug` | Hex радио/ZCL, адреса, счётчики и все более высокие уровни |
| `info` | Старт/завершение, MQTT-команды, результат транспорта, предупреждения/ошибки |
| `warn` | Отклонённые команды, неподдержанные отчёты, предупреждения/ошибки |
| `error` | Только ошибки |

console=true выводит в stderr; file="" отключает файл. Должен остаться хотя бы один вывод. max_size_mb: `1..1024` MiB; backups: `0..100`.

Ротация выполняется перед полной записью, превышающей порог; одна очень длинная строка может оказаться больше него. Старые файлы: zigbeemqttlink.log.1…N, .1 — самый свежий. backups=0 удаляет предыдущий файл при ротации. Изменения настроек требуют перезапуска; используйте ротацию вместо ручного удаления открытого лога.

## Запуск через systemd

Адаптируйте [zigbeemqttlink.service.example](zigbeemqttlink.service.example). Пример рассчитан на /opt/zigbeemqttlink, пользователя zigbeemqttlink и группу dialout. Сначала создайте пользователя и предоставьте права на каталоги базы/описаний/логов. Установите подходящего владельца бинарника и файлов с учётными данными.

Для нестандартных путей исправьте ReadWritePaths; для ARM64 — ExecStart. После подготовки:

```bash
sudo cp zigbeemqttlink.service.example /etc/systemd/system/zigbeemqttlink.service
sudo systemctl daemon-reload
sudo systemctl enable --now zigbeemqttlink.service
sudo systemctl status zigbeemqttlink.service
journalctl -u zigbeemqttlink.service -f
```

Файл и консоль/journal могут работать одновременно. Основной конфиг требует `systemctl restart zigbeemqttlink.service`; перечитывание моделей — нет.

## Диагностика

| Симптом | Что проверить |
|---|---|
| devices=0 после переноса | Путь/копию рабочей JSON-базы; поставляемая база пуста |
| Неизвестный сетевой адрес | Нет записи/сменился NWK; проверьте базу и дождитесь announce/interview |
| Команда старта проигнорирована | Retained-повтор; отправьте новую команду без retain |
| Транспорт принял, устройство не изменилось | Следующий отчёт, endpoint, описание и доступность спящего узла |
| Неподдержанное свойство TS0601 | Точного производителя и корректные DP |
| Описание отклонено | Ошибку JSON/селектора/типа/диапазона; старый реестр остаётся |
| Веб недоступен с другого компьютера | Включение веба, адрес прослушивания, состояние сервиса и доступ к порту |
| Нет прав UART | Путь, группы пользователя и другой процесс на координаторе |
| Нет info/debug-логов | Текущий фильтр уровня |
| Недоступна замена | Сопряжённую замену и совпадение модели/производителя |

Health/счётчики различают входящие кадры, преобразованные и опубликованные отчёты, MQTT-команды и отказы. Готовое MQTT-подключение и кэш состояний сами по себе не подтверждают поступление радио-сообщений.

## Разработка и проверка

Внутренние пакеты разделяют транспорт, разбор, хранение, описания моделей, логи и MQTT/HTTP. main.go — точка входа в корне. Обычные сопоставления добавляйте в JSON; новые протокольные возможности и специализированные обработчики — в Go.

Тестов/симулятора в проекте нет. Сборка, статический анализ и проверка конфига:

```bash
go vet -buildvcs=false ./...
go build -buildvcs=false -trimpath -o dist/zigbeemqttlink .
./dist/zigbeemqttlink -check-config -config ./config.json
```

Примеры протокольных сообщений, перечитывание/проверка описаний, база, MQTT/HTTP и логирование проверялись отдельными инструментами разработки. После переименования проверяются сборки и CLI. Проверочные инструменты в проект не включены. Физический координатор и полный набор прошивок были недоступны; программные проверки не означают универсальную совместимость оборудования.
